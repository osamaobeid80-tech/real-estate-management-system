1 نطاق النظام والبيئة المستهدفة

يُبنى النظام كتطبيق ويب واحد (Single Codebase) متوافق مع منهج Responsive Design، يعمل كـ Progressive Web App (PWA) قابل للتثبيت على سطح المكتب والجوال، بدلاً من تطوير تطبيقات منفصلة لكل نظام تشغيل — وهو الحل الأمثل لمكتب عقاري صغير من ناحية التكلفة وسرعة الصيانة.

القرار التصميمي: واجهة واحدة متجاوبة (Responsive Web + PWA) تُلغي الحاجة لتطبيقات Native منفصلة على Android/iOS، مع الحفاظ على تجربة قريبة من التطبيقات الأصلية (أيقونة على الشاشة الرئيسية، عمل دون اتصال جزئي، إشعارات دفع مستقبلاً).

3.4 التقارير الدورية (Reports)

في نموذج Backend مستقل (غير Static)، تُبنى نقاط نهاية تجميعية (Aggregation Endpoints) بدلاً من حساب كل شيء في العميل عند نمو حجم البيانات:

التقريرMethodالمسار المقترحالإخراج
ملخص الإشغالGET/reports/occupancyعدد الوحدات: مؤجرة/شاغرة/صيانة/محجوزة
الدفعات المستحقة قريبًاGET/reports/upcoming-dues?days=30قائمة دفعات تستحق ضمن مدى زمني
الدفعات المتأخرةGET/reports/overdueدفعات فات تاريخ استحقاقها دون سداد
الإيرادات الشهريةGET/reports/revenue?from=&to=إجمالي المسدد مقابل المستهدف لكل شهر
تصدير CSV/PDFGET/reports/export?type=payments&format=csvملف قابل للتنزيل (يتطلب Backend فعلي)
ملاحظة تنفيذية: في النسخة التجريبية الحالية (Static/PWA) تُحسب التقارير على العميل (Client-side aggregation) من بيانات /tables/* مباشرة، وهذا مناسب لمكتب صغير. أما نسخة React/Backend فتستخدم فعليًا تجميعات PostgreSQL عبر /reports/occupancy و/reports/unit-types و/reports/payment-status و/reports/revenue، وتوفر /reports/export?format=pdf لإنشاء PDF على الخادم.

3.6 تصميم المصادقة (Authentication)

  • الوضع الحالي (Static/PWA تجريبي): لا توجد مصادقة خلفية حقيقية — أي تحقق في JavaScript يمكن قراءته وتجاوزه من مصدر الصفحة، ولا يُعتبر حماية فعلية.
  • الوضع الموصى به عند بناء Backend فعلي: مصادقة عبر JWT (JSON Web Token) قصير الصلاحية + Refresh Token، مع تشفير كلمات المرور بخوارزمية bcrypt/argon2.
  • صلاحيات مبنية على الأدوار (RBAC): مسؤول النظام (كل الصلاحيات)، موظف إدخال بيانات (إضافة/تعديل دون حذف)، مستخدم عرض فقط (قراءة فقط + تقارير).
  • كل طلب API يحمل Authorization: Bearer <token> ويُتحقق من الدور قبل تنفيذ أي عملية كتابة/حذف على الخادم (وليس فقط إخفاء الزر في الواجهة).

معيار الاختيار الموصى به لمكتب عقاري صغير

لعدد وحدات محدود (حتى ~500 وحدة) وفريق تقني صغير أو معدوم: الحل الحالي Static PWA يكفي تمامًا مع أقل تكلفة تشغيلية. عند الحاجة لمصادقة حقيقية، صلاحيات دقيقة، تقارير PDF، أو نمو العملاء لعدة مكاتب/فروع، يُوصى بالترقية إلى Node.js + PostgreSQL + React لتوازنه بين السرعة والتكلفة وسهولة التوظيف المحلي لهذه المهارات.

5 الأمن والامتثال والقيود

5.1 التشفير

  • فرض HTTPS/TLS 1.2+ على كل الاتصالات (شرط أساسي لعمل PWA أيضًا).
  • تشفير كلمات المرور بخوارزمية Argon2/bcrypt عند بناء Backend فعلي — عدم تخزينها كنص صريح مطلقًا.
  • تشفير الحقول الحسّاسة في قاعدة البيانات وقت التخزين (Encryption at Rest) لرقم الهوية/جوال المستأجر عند استخدام قاعدة بيانات مؤسسية.
  • عدم تضمين أي مفاتيح API أو أسرار في كود العميل (Client-side) — يخالف هذا مبدأ الأمان الأساسي لأي تطبيق ويب.

5.3 النسخ الاحتياطي (Backup)

  • نسخة احتياطية يومية تلقائية لقاعدة البيانات (Automated Daily Backup) بالاحتفاظ بها 30 يومًا على الأقل.
  • نسخة كاملة أسبوعية + نسخة شهرية بالاحتفاظ الطويل (Cold Storage) لمدة سنة على الأقل لأغراض تدقيقية/عقدية.
  • اختبار دوري لاستعادة النسخ الاحتياطية (Restore Drill) كل 3 أشهر للتأكد من صلاحيتها.
  • تصدير احتياطي يدوي (CSV/JSON) متاح للمسؤول عند الحاجة لأرشفة خارج النظام.

5.4 حماية البيانات الشخصية والامتثال المحلي

  • الالتزام بـ نظام حماية البيانات الشخصية السعودي (PDPL) الصادر عن SDAIA: جمع الحد الأدنى من بيانات المستأجر اللازمة للعقد فقط، وعدم مشاركتها مع طرف ثالث دون موافقة.
  • سجل تدقيق (Audit Log) لكل من أضاف/عدّل/حذف سجل مستأجر أو دفعة، لأغراض المساءلة.
  • حق المستأجر بطلب الاطلاع على بياناته المحفوظة أو حذفها بعد انتهاء العقد وفق المهلة النظامية للاحتفاظ بالسجلات المالية/العقدية.
  • الاحتفاظ بأرقام الهوية/السجلات التجارية بصيغة مقنّعة جزئيًا (Masking) في الشاشات العامة، وإظهارها كاملة فقط لمسؤول النظام.

6 التجربة والواجهة (UX/UI)

  • واجهة عربية RTL كاملة كلغة أساسية، مع بنية جاهزة لإضافة تبديل لغة EN (LTR) مستقبلاً دون إعادة هيكلة CSS (استخدام dir منطقي وليس تثبيت يمين/يسار).
  • خط Cairo/Tajawal لدعم القراءة العربية بوضوح على كل الأحجام.
  • تباين ألوان يحقق WCAG AA على الأقل لسهولة القراءة لكبار المستخدمين في المكتب العقاري.

8.2 حالات اختبار وظيفية نموذجية

  • إنشاء وحدة جديدة بدون رقم عقد ← يجب أن تُصنَّف تلقائيًا "شاغرة".
  • تسجيل سداد دفعة ← يجب أن يزيد payments_paid بمقدار 1 تلقائيًا في سجل الوحدة.
  • دفعة تجاوز تاريخ استحقاقها دون سداد ← تنتقل حالتها تلقائيًا إلى "متأخرة" وتظهر في تنبيهات لوحة التحكم.
  • مستخدم بدور "عرض فقط" يحاول حذف وحدة عبر واجهة مُعدَّلة يدويًا في الأدوات المطوّرة ← يجب أن يُرفض الطلب من الخادم (401/403) وليس فقط إخفاء الزر.
  • البحث عن مستأجر برقم جواله الجزئي ← يجب أن تظهر جميع النتائج المطابقة.

9 النشر والصيانة والتسليم

9.1 خط أنابيب CI/CD مقترح (عند تطوير Backend كامل)

1. Commit & Push

دفع الكود إلى مستودع Git (GitHub/GitLab) على فرع feature.

2. Lint + Unit Tests

تشغيل تلقائي عبر GitHub Actions/GitLab CI عند كل Pull Request.

3. Build

بناء صورة Docker للـBackend وحزمة Frontend (Vite/Webpack Build).

4. Integration Tests

تشغيل اختبارات API آلية على بيئة Staging.

5. Deploy Staging

نشر تلقائي لبيئة تجريبية للمراجعة اليدوية.

6. Approval Gate

موافقة يدوية من مسؤول المشروع قبل الإصدار للإنتاج.

7. Deploy Production

نشر تدريجي (Rolling Deploy) + نسخة احتياطية قبل الترحيل.

9.2 النشر الفعلي لهذا التسليم (Static PWA)

هذا التطبيق مبني كموقع ثابت (Static Site) ضمن بيئة Genspark. النشر يتم عبر:

  • تبويب "Publish" في المحرر: نشر بضغطة واحدة على رابط *.gensparkspace.com (معاينة عامة مباشرة).
  • Hosted Deploy (عند الطلب صريحًا): نشر على *.vip.gensparksite.com مع قاعدة بيانات D1 حقيقية تُنشأ تلقائيًا من نفس المخطط، وربط اختياري بدومين مخصص.
  • لا حاجة لأي إعداد خادم يدوي (Nginx/Docker) في هذه المرحلة — البنية بأكملها مُدارة من المنصة.
